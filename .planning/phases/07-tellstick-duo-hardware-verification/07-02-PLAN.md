## Key Technical Context

### tdtool Commands
- `tdtool --list` - Lists all configured devices, returns exit code 0 on success
- `tdtool --on <id>` - Transmits ON command, returns exit code 0 if transmitted (per D-07-02)
- `tdtool --off <id>` - Transmits OFF command, returns exit code 0 if transmitted

### Exit Code Behavior
Per RESEARCH.md and tdtool/main.cpp:
- Exit code 0 = TELLSTICK_SUCCESS (command transmitted)
- Exit code 1 = TELLSTICK_ERROR_NOT_FOUND or other error
- Non-zero = Failure (device not found, communication error, etc.)

### Verification Scope (Per Decisions)
- D-07-08: On/off commands only - dimming, bell, learn out of scope
- D-07-09: Test one representative device - testing all devices not required
- D-07-10: Turn on → verify → turn off → verify cycle
- D-07-01: Minimum viable is "tdtool lists configured devices"

### Important: 433 MHz is One-Way
- Exit code 0 means "command transmitted" NOT "device acknowledged"
- No device state feedback possible without external observation (visual, RF sniffer)
- Verification confirms transmission success only per RESEARCH.md
</context>

|----------|-------------|
| tdtool → telldusd | Commands sent via Unix socket within container namespace |
| telldusd → USB | Commands transmitted to TellStick Duo over USB |
| TellStick → RF | 433 MHz radio transmission (one-way, unauthenticated) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-02-01 | Spoofing | RF command interception/replay | accept | 433 MHz protocol limitation; out of scope for v1 modernization (original protocol behavior) |
| T-07-02-02 | Information Disclosure | Device list exposed via tdtool | accept | Local container access only; operator must have Docker access |
| T-07-02-03 | Denial of Service | Command flooding | accept | Single-device testing per D-07-09 mitigates excessive RF traffic |
</threat_model>
